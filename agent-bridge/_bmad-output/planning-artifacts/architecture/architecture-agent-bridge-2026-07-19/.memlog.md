- (direction) Architect the PRD-approved node-pty launcher (Topology A). Gating problem to resolve: PRD has dashboard.js own the PTY, but node-pty children die when the dashboard process exits, and Ali's workflow restarts the dashboard on every code edit -> every edit would kill all agents. Architecture must decouple PTY lifecycle from dashboard lifecycle.
- (decision) AD-1 PTY OWNERSHIP OUT OF DASHBOARD. Binds: launcher, dashboard.js, all agent processes. Prevents: dashboard restart/crash killing running agents (regression vs tmux daemon). Rule: the node-pty master fd is held by a standalone, detached (setsid/.unref) per-agent launcher process — NEVER by the dashboard or MCP server process. The dashboard is a pure client.
- (decision) AD-2 LOG FILE IS THE DURABLE SOURCE OF TRUTH. Binds: launcher, dashboard SSE, unrouted-reply detector. Prevents: output loss across any consumer restart + gives late-joiners full history. Rule: the owner process persists every PTY byte append-only to .neohive/agent-log-{agent}.jsonl ({ts,agent,data} per line, existing convention). Consumers TAIL this file; the PRD 1MB in-memory ring buffer is a live-latency optimization layered on top, not the durability mechanism.
- (decision) AD-3 SINGLE-WRITER PTY VIA PER-AGENT IPC. Binds: launcher, dashboard terminal widget, input path. Prevents: multiple-writer races to the PTY master; coupling input to SSE. Rule: live input + resize flow over a per-agent unix domain socket .neohive/pty-{agent}.sock; the owner process is the SOLE writer to pty.write(). Multiple readers allowed; last input connection wins (PRD OQ-3).
- (decision) AD-4 TMUX IS DISPLAY-ONLY, NEVER A DEPENDENCY. Binds: launcher, tmux integration (PRD FR-9). Prevents: re-coupling durability/capture to tmux while still allowing operator attach. Rule: the owner process MAY be launched inside a tmux pane so operators keep tmux attach, but PTY ownership + capture + routing MUST function identically with no tmux present. [ADOPTED from PRD FR-9]
- (decision) AD-5 GRACEFUL DEGRADATION TO TMUX LAUNCHER. Binds: dashboard launch endpoint. Prevents: hard launch failure when node-pty native addon is unavailable. Rule: if node-pty cannot load, surface a warning and fall back to lib/tmux-cli-launcher.js; never hard-block the launch. [ADOPTED from PRD OQ-1/OQ-4]
- (decision) AD-6 REGISTRY REMAINS SINGLE LIVENESS AUTHORITY. Binds: launcher, agents.json, heartbeat, watchdog. Prevents: a competing agent-liveness model. Rule: the owner writes the agent PID to agents.json on spawn and fires agent_exit + registry cleanup on child exit; watchdog/heartbeat semantics are unchanged. [ADOPTED from PRD FR-7/FR-8]
- (decision) AD-7 CAPTURED STREAM IS SENSITIVE. Binds: log writer, retention. Prevents: leaking tokens/keys that pass through agent terminals into world/less-guarded storage. Rule: agent-log-{agent}.jsonl inherits .neohive perms; a redaction pass strips known secret patterns before write; retention matches the messages.jsonl policy.
- (constraint) node-pty pinned ^1.1.0 — reality-checked: already declared in package.json optionalDependencies and installed with prebuilds present (node_modules/node-pty/prebuilds). Native C++ addon; Windows backend out of v1 scope (PRD Non-Goal).
- (constraint) Inherited from CLAUDE.md architecture: multiple MCP server processes share the .neohive/ filesystem (append-only messages/history, per-agent consumed files, PID-based stale detection, SSE via fs.watch). The launcher must fit this filesystem-as-bus model — hence AD-2 log-file source of truth aligns with existing patterns.
- (question) OQ-1 GATING: does the team accept the standalone per-agent owner-process design? It is heavier than the PRD's implicit 'dashboard spawns the PTY', but it is the ONLY form of Topology A that survives dashboard restarts. This tightens (does not contradict) the PRD; flag if the PRD intended the dashboard to literally own the fd.
- (question) OQ-2: per-agent owner process (recommended, matches neohive's one-process-per-agent grain) vs a single central PTY supervisor daemon holding all masters. Per-agent avoids a central singleton with its own health/lifecycle burden.
- (question) OQ-3: dashboard reconnect protocol after a restart — re-tail log file (history) + reconnect per-agent socket (live I/O). Define handshake: how the dashboard rediscovers live agents (scan .neohive/pty-*.sock + agents.json).
- (question) OQ-4: default PTY dimensions before a client reports size — PRD assumes 220x50. Confirm; owner must apply a default and honor later resize over the socket (AD-3).
